# 写真記事ジェネレーター 実装仕様・Codex向け指示

## 0. 目的と作業方針

既存の写真管理アプリに、選択した写真とユーザーが入力した文章から、雑誌・新聞の紙面を模した**1ページの画像**を作成する機能を追加する。既存の写真管理、タグ付け、選択UIと自然に連携させること。画像生成AIによる写真の再生成は行わず、**元写真をレイアウト・クロップして組版する**。

**最初に既存リポジトリを調査し、既存のアーキテクチャ、UI、画像読み込み、データ永続化、テスト方式を把握してから実装計画を提示すること。** 既存コードを見ずにファイル名やクラス名を決め打ちしない。実装は段階的に進め、各フェーズの完了時に変更点・動作確認結果・未対応事項を報告する。

### 開発環境に関する制約

- 既存の `AGENTS.md` とリポジトリ内の開発規約を優先する。
- 既存の `.venv` は作成・削除・再作成・置換・変更しない。
- 明示的な許可なく `uv run`、`uv sync` 等、既存 `.venv` を変更し得るコマンドを実行しない。
- 検証用に**別の**仮想環境を作成することは許容する。ただし既存 `.venv` と混同せず、既存環境へ影響を与えないこと。
- 新規依存の追加は最小限とし、必要なら追加理由と代替案を説明する。
- OS・パス・フォント環境は決め打ちしない。Windows 11 と WSL2 を含む実行環境を考慮する。

## 1. ユーザー体験

1. 写真一覧から1〜6枚（初期実装の上限）を選択する。
2. 「記事画像を作成」等の操作で編集画面を開く。
3. フォーマットを選ぶ。写真枚数や向きによって利用可能なテンプレートを絞る。
4. タイトル、サブタイトル、リード文、本文、写真別キャプションを入力する。プロフィール特集ではプロフィール項目も入力する。
5. ライブプレビューで完成イメージを確認する。
6. 「別のレイアウト」を押すと、**写真と入力テキストを保持したまま**レイアウトを再生成する。
7. 必要ならメイン写真、写真の順序、クロップ位置、テンプレート、シード値を変更する。
8. PNGまたはJPEGで保存する。編集可能なプロジェクトも保存・再読込できるようにする。

写真へのタグやEXIFは、初期段階では参照可能な情報として扱う。自動記事生成は行わず、記事文章はユーザー入力を基本とする。

## 2. 初期対応フォーマット（4種類）

### A. 雑誌特集型

- 想定写真枚数: 2〜6枚。
- 大きなメイン写真、タイトル、リード文、2〜3段組の本文、補助写真、キャプション。
- 雑誌名風のヘッダー、カテゴリ名、ページ番号、細い罫線をオプションで配置。
- バリエーション: 上部全面ヒーロー写真／左右分割／下部写真グリッド。

### B. 新聞記事型

- 想定写真枚数: 1〜3枚。
- 大見出し、日付、リード文、本文の複数段組、写真とキャプション。
- 明朝系フォント、罫線、控えめな色使い、新聞風の情報密度。
- バリエーション: 写真中央／写真左寄せ／大見出し＋小写真。
- 初期実装は**横書き**。縦書きは対象外。

### C. フォトエッセイ型

- 想定写真枚数: 2〜5枚。
- 写真を大きく見せ、余白を広く取る。短めの文章とキャプション。
- バリエーション: 1枚大きく＋小写真／写真2列／写真を縦方向に連ねる。
- 写真の縦横比をできるだけ活かし、不自然な切り抜きを避ける。

### D. プロフィール特集型（人物・動物の個体紹介）

- 想定写真枚数: 1〜6枚。
- 対象の名前、任意のサブタイトル、メインポートレート、**自由なラベル・値のプロフィール項目**、紹介記事、補足記事、サブ写真。
- 人物・動物のどちらにも使えるよう、「性別」「生年月日」「所属」「好物」などの項目名は固定しない。
- プロフィール項目は追加・削除・並べ替え可能とする。
- バリエーション: プロフィールカード型／インタビュー・Q&A型／時系列ドキュメンタリー型。
- Q&A型の質問と回答はユーザー入力とし、入力されていない内容を捏造しない。
- 将来的にタグや被写体エンティティとの関連付けを追加できる設計にするが、初期実装では既存データモデルの大規模変更を必須にしない。

### 共通デザイン要素

- 文字階層: タイトル、サブタイトル、リード、見出し、本文、キャプション。
- グリッド、余白、段組み、整列、罫線、ページ番号、日付、カテゴリ。
- 日本語の折り返し・禁則処理を考慮する。日本語フォントが利用できない場合はフォールバックする。
- 写真は元画像の色を維持する。新聞のモノクロ化等は明示的なスタイル指定時のみ。
- 生成画像内の文章はすべてユーザー入力または明示的なメタデータに由来し、架空の事実を自動挿入しない。

## 3. データモデル

UI・レイアウト計算・レンダリング・保存形式を分離する。以下は**概念モデル**であり、既存コードの命名規約に合わせて調整してよい。

```json
{
  "schema_version": 1,
  "format": "profile",
  "page": {"preset": "A4_portrait", "dpi": 300},
  "seed": 12345,
  "template_id": "profile_card_01",
  "title": "コハルの一日",
  "subtitle": "レッサーパンダ個体紹介",
  "lead": "ユーザー入力のリード文",
  "sections": [
    {"kind": "article", "heading": "コハルのこと", "body": "ユーザー入力の本文"},
    {"kind": "article", "heading": "最近の様子", "body": "ユーザー入力の補足記事"}
  ],
  "profile": {
    "name": "コハル",
    "fields": [
      {"label": "生年月日", "value": "2019年5月12日"},
      {"label": "性別", "value": "メス"},
      {"label": "所属", "value": "○○動物園"}
    ]
  },
  "photos": [
    {
      "source_id": "existing-photo-id-or-null",
      "source_path": "path/to/photo.jpg",
      "role": "hero",
      "caption": "ユーザー入力の説明",
      "crop": {"focus_x": 0.5, "focus_y": 0.5}
    }
  ]
}
```

- プロジェクトの保存形式はJSON等の可読な形式を優先する。
- 写真参照は既存の写真IDを優先し、必要ならパスをフォールバックとして保持する。絶対パスのみへの依存は避ける。
- 画像が移動・削除された場合はクラッシュせず、欠損写真を通知する。
- `schema_version` を持たせ、将来のマイグレーションを考慮する。
- `seed`、`template_id`、写真順、クロップ設定を保存し、同じ環境・同じ入力で再現可能にする。

## 4. レイアウトエンジン

### 設計

`Document` → `Template selection` → `Layout calculation` → `Render` → `Export` の責務を分離する。

- テンプレートはJSON、dataclass等で**宣言的に**定義し、UIコードへ座標を直接埋め込まない。
- テンプレートは対応フォーマット、必要写真枚数、推奨縦横比、各スロットの役割・制約、余白、段組み、フォントスタイルを持つ。
- スロット種別の例: `hero_photo`, `photo`, `title`, `lead`, `body`, `caption`, `profile`, `header`, `footer`, `rule`。
- レイアウト座標はページサイズに対する論理単位（ptまたはmm等）で管理し、出力DPIと分離する。
- レイアウト選択は写真枚数、縦横比、文章量、プロフィール項目数を評価して候補を選ぶ。
- 乱数は局所的なseed付き生成器を使用し、グローバルな乱数状態に依存しない。
- ランダム化するのはテンプレート、写真順（メイン写真指定は尊重）、アクセント、配置バリエーションなど**安全な範囲**に限定する。
- ユーザーが指定した写真・本文・プロフィールはランダム化で消さない。

### 文章量への対応

- Qtのテキストレイアウト機能（`QTextDocument` 等）で実際の描画高さを測定する。
- まずテンプレート選択、段組み、文章エリアの配分で調整する。
- 最小フォントサイズを設け、無制限に縮小しない。
- 入力文章が収まらない場合は、**黙って切り捨てず**、オーバーフロー警告と必要な調整方法を示す。
- MVPでは1ページ完結を優先し、自動複数ページ化は将来拡張とする。
- レンダリング前に、はみ出し、写真・文字の重なり、余白不足を検証する。

### 写真の配置

- 元写真の縦横比を保持し、スロットに応じて `contain` または `cover` を選ぶ。
- `cover` 時のクロップ中心を調整可能にする。
- 元ファイルを変更しない。サムネイルはプレビュー用、書き出しは可能な限り元画像を使用する。
- EXIF Orientationを正しく反映し、異常に大きな画像でもメモリ使用量に配慮する。

## 5. PySide6実装案

既存アプリに合わせて以下を検討する。強制的に新規フレームワークを導入しない。

| 責務 | 第一候補 |
|---|---|
| 編集UI | PySide6 Widgets（既存UIに合わせる） |
| プレビュー | `QGraphicsView` / `QGraphicsScene` または既存のプレビュー機構 |
| 描画 | `QPainter`, `QImage` |
| 文章の組版 | `QTextDocument` / Qtテキストレイアウト |
| 画像出力 | `QImageWriter` 等 |
| テンプレート定義 | JSON / Python dataclass |
| 将来のPDF出力 | `QPdfWriter`（初期必須ではない） |

プレビューとエクスポートは**同じレイアウト計算結果**を使い、プレビューと出力の見た目の差を最小化する。重い処理はUIスレッドを長時間ブロックしない。Qtオブジェクトのスレッド制約に注意する。

## 6. 編集画面の要件

- 選択写真のサムネイル一覧、メイン写真の指定、並べ替え。
- フォーマットとテンプレートの選択。
- タイトル、サブタイトル、リード、複数セクションの本文、写真別キャプションの入力。
- プロフィール特集では名前と自由項目の編集、任意のQ&A入力。
- ページプレビュー、ズーム、レイアウト再生成、シード値の確認・固定。
- 文章がはみ出した場合の明確な警告。
- PNG/JPEG出力先と品質・解像度の指定。
- 保存済みプロジェクトの再編集。
- 既存の写真選択やショートカット、ウィンドウ操作との整合性を保つ。

## 7. 出力と品質

- 初期ページサイズはA4縦相当。初期出力は300 DPI相当（約2480×3508 px）。必要に応じてプレビューは低解像度にする。
- PNG、JPEGをサポート。JPEGの圧縮品質を指定可能にする。
- 出力画像は元写真のアスペクト比を壊さず、テキストが欠けないこと。
- 日本語、英数字、句読点、長い単語、改行、空文字、長文で崩れないこと。
- 保存時は既存ファイルの上書き確認とエラーハンドリングを行う。
- 生成画像と編集用プロジェクトは別物として扱う。

## 8. 実装フェーズ

### Phase 1: 調査と最小縦切り

1. 既存アプリの写真選択、画像ロード、保存先、UI構成、テスト構成を調査する。
2. 実装予定のモジュール構成と依存関係を短く提示する。
3. 選択写真を受け取り、雑誌特集型の**1テンプレート**をプレビュー・PNG出力できる最小実装を作る。
4. 日本語タイトル、本文、キャプションの描画を確認する。

### Phase 2: 4フォーマット対応

1. 新聞記事型、フォトエッセイ型、プロフィール特集型を追加する。
2. プロフィールの自由項目編集、セクション編集、写真順・メイン写真選択を実装する。
3. 各フォーマットで最低1つの安定したテンプレートを実装する。

### Phase 3: バリエーションと品質

1. 各フォーマットに複数テンプレート（目標3パターン以上）を追加する。
2. シード付きランダム再生成、写真のクロップ位置調整、文章オーバーフロー検知を実装する。
3. プレビューと高解像度出力の一致を確認する。

### Phase 4: 永続化と仕上げ

1. プロジェクト保存・再読込、JPEG出力、エラー表示を追加する。
2. 自動テストと目視確認用のサンプルデータを整備する。
3. UIの使い勝手、処理速度、メモリ使用量を改善する。

各フェーズで大規模な既存機能の改修を避ける。未確定の仕様や影響の大きい変更は実装前に相談すること。

## 9. テスト・受け入れ条件

- [ ] 既存写真一覧から選択した写真で記事作成画面を開ける。
- [ ] 4フォーマットすべてで少なくとも1つの紙面を生成できる。
- [ ] プロフィール項目は任意のラベル・値を追加・削除・並べ替えできる。
- [ ] 入力した文章や写真がレイアウト再生成で失われない。
- [ ] 同一シード・同一入力・同一テンプレートで再現可能な配置になる。
- [ ] 写真1枚、上限枚数、縦長・横長混在で破綻しない（非対応組合せは明示する）。
- [ ] 長文時に文字が無言で欠けず、オーバーフローを通知する。
- [ ] 日本語テキストとEXIF Orientationを正しく処理する。
- [ ] プレビューとPNG/JPEG書き出しで配置が一致する。
- [ ] プロジェクトを保存・再読込して編集を続けられる。
- [ ] 元写真および既存 `.venv` を変更しない。
- [ ] 既存の写真管理機能に回帰不具合がない。

### 推奨テストケース

- 1枚の横長写真＋短文、6枚の縦横混在写真＋複数段落。
- 0件／3件／10件のプロフィール項目。
- 日本語の長い見出し、改行、全角句読点、英数字混在。
- 長すぎる本文、空欄の任意項目、写真ファイル欠損。
- 同じseedでの連続生成とseed変更後の再生成。
- 高解像度出力時のメモリ使用量とUI応答性。

## 10. 初回のCodexへの実行指示

**まずこの仕様書と既存 `AGENTS.md` を読み、リポジトリを調査してください。** 現在の写真選択・表示・データ管理の構造を要約し、追加モジュール、データモデル、UI導線、テスト方針を提案してください。実装はPhase 1から始め、既存機能への影響を最小化してください。大規模なリファクタリングや新規依存の導入が必要なら、その理由を説明してから進めてください。既存 `.venv` を変更しないでください。

## 11. 将来の拡張（初期実装の必須要件ではない）

- 図鑑・観察記録型、トラベル誌型の追加。
- A4見開き、複数ページ、SNS向け正方形・横長キャンバス。
- 縦書き組版、PDF出力。
- タグからカテゴリ名や写真候補を自動提案。
- EXIFの撮影日時・焦点距離・絞り等を小さな情報欄に挿入。
- 被写体エンティティとプロフィールの紐付け。
- ユーザー定義テンプレートとプリセットの共有。
- AIによる文章校正・見出し提案（明示的な操作がある場合のみ）。
