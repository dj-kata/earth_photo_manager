# 写真記事エディター：構造化入力UI拡張仕様（Codex向け）

## 背景と目的

既存のPySide6製写真管理アプリには、写真記事生成エディターと4形式（雑誌特集型・新聞記事型・フォトエッセイ型・プロフィール特集型）がある。現状のエディターは「フォーマット」「タイトル」「本文」「選択写真」「写真ごとのキャプション」程度の入力に留まる。既存の描画機能を活かしつつ、雑誌・新聞・個体紹介らしい複数の情報要素を入力・編集・描画できるよう拡張する。

**重要：まずリポジトリの既存実装とAGENTS.mdを確認する。既存アーキテクチャ、永続化方式、プレビュー更新方式に合わせる。既存の写真選択・画像出力・クリップボードコピー・テンプレートを壊さない。**

## 対象となる記事の構造

記事データをテンプレートから独立した共通モデルとして管理する。推奨フィールド（命名は既存コードに合わせてよい）：

```json
{
  "schema_version": 2,
  "format": "profile",
  "title": "さち",
  "subtitle": "のんびり過ごすコアラの一日",
  "lead": "この個体の魅力を紹介します。",
  "metadata": {"category": "個体紹介", "author": "", "date": ""},
  "profile": [
    {"id": "p1", "label": "生年月日", "value": "2018年生まれ"},
    {"id": "p2", "label": "性別", "value": "メス"},
    {"id": "p3", "label": "所属", "value": "○○動物園"}
  ],
  "sections": [
    {"id": "s1", "heading": "さちの紹介", "body": "性格や特徴を紹介する文章。"},
    {"id": "s2", "heading": "最近の様子", "body": "撮影時のエピソード。"}
  ],
  "pull_quote": "お気に入りの一枚",
  "photos": [
    {"photo_id": "existing-id", "role": "hero", "caption": "木の上で休むさち", "crop": null}
  ]
}
```

これは概念例。写真参照は既存の管理IDやパスの仕組みを優先し、互換性のあるモデルにする。入力値を安全に扱い、保存形式を変更する場合は既存データの読み込み・移行を考慮する。

## 入力UIの要件

1. **共通の基本情報**：タイトル、サブタイトル、リード文、カテゴリ、日付、著者（任意）。既存タイトル・本文の入力値は移行または互換表示する。
2. **本文セクション**：小見出し＋本文を1組として0件以上追加・削除・並べ替えできる。既存の単一本文は初期セクションとして取り込むなど、データを失わない方法を採用する。
3. **プロフィール項目**：項目名＋値のペアを0件以上追加・削除・並べ替えできる。項目名は自由入力（生年月日、性別、所属、好物、性格などを想定）。プロフィール型以外ではUIを折り畳むか非表示にしてよいが、値は保持する。
4. **引用・強調文**：任意の短い文章を1件入力可能にする。未入力なら領域を詰める。
5. **写真リスト**：既存の写真選択を維持。写真ごとのキャプション編集に加え、可能ならメイン写真（hero）の指定と写真の並べ替えを実装する。元写真の編集・破壊的変更はしない。
6. **操作性**：左側をスクロール可能な入力パネルとし、基本情報・記事セクション・プロフィール・写真などをグループ化する。右側のプレビューを維持。文字入力のたびに重いフルレンダリングをしないよう、既存の仕組みを確認し必要ならデバウンスする。
7. **形式切替**：4形式の切替で入力済みの値を破棄しない。形式ごとに使わない項目は保持し、表示だけ切り替える。

## フォーマットごとの描画要件

- **雑誌特集型**：タイトル、サブタイトル、リード、複数セクション、メイン写真、補助写真とキャプション、任意の引用文を活用。大きな写真と余白、見出しの階層を重視。
- **新聞記事型**：見出し、リード、日付・カテゴリ、複数セクションを段組みで配置。写真とキャプションを本文と整合させる。見出しや本文の日本語折り返しを検証。
- **フォトエッセイ型**：写真を主役に、タイトル・短文セクション・写真キャプションを配置。文章が少ない場合も破綻しない。
- **プロフィール特集型**：メイン写真、名前（タイトル）、サブタイトル、プロフィール項目の一覧、リード、複数の紹介セクション、補助写真とキャプションを配置。プロフィールの数に応じて表の高さを変える。写真1枚でも成立させる。

各形式のレイアウトを共通の入力データから生成する。空欄要素のための不自然な余白を残さない。写真0枚、1枚、複数枚や、項目数の差に対する挙動を定義する。文字や写真の重なり、本文のクリッピング、意図しない極小フォントを避ける。収まらないときは、複数ページ対応が既にあるなら利用し、なければ少なくとも明確なオーバーフロー警告を出す。黙って切り捨てない。

## レイアウトのバリエーション

既存のテンプレート／シード機構を確認し、あるなら活用する。無ければ今回の入力UI拡張を優先し、将来追加しやすい構造にする。ランダム再生成を実装する場合は、シード固定で再現可能とし、文章・写真の入力内容は変えずにレイアウトだけ変更する。プロフィール型の将来候補：カード型、インタビュー型、時系列型。これらを一度に無理に実装しない。

## 実装順序

1. **調査と計画**：現行のデータモデル、入力ウィジェット、テンプレート描画、プレビュー、画像保存、テスト、AGENTS.mdを調査。変更対象と互換性リスクを提示。
2. **モデル拡張**：共通記事データ、プロフィール項目、セクション、メタデータを追加。既存データと互換性を確保。
3. **UI拡張**：追加・削除・並べ替えを含むフォーム、写真の役割指定を実装。スクロールと入力保持を確認。
4. **描画拡張**：まずプロフィール特集型でプロフィール一覧と複数セクションを表示。その後、他3形式へ適用。
5. **品質改善**：可変文章量・可変項目数・写真枚数の検証、レイアウト警告、テスト、必要なら再生成機能。

各段階で変更ファイル・動作確認結果・残課題を報告する。大規模な再設計や依存追加が必要な場合は実施前に相談する。

## 受け入れ条件

- プロフィール特集型で「さち」の写真1枚、タイトル、サブタイトル、プロフィール3項目、紹介セクション2件を入力すると、プレビューとPNG出力の両方に反映される。
- プロフィール項目と記事セクションを追加・削除・並べ替えでき、変更後のプレビューに反映される。
- フォーマットを切り替えて戻しても入力データが消えない。
- 雑誌・新聞・フォトエッセイ型でも、複数セクションと必要な共通情報が表示される。
- 写真キャプションとメイン写真指定が正しい写真に紐づく。
- 空欄や長文でレイアウトが破綻せず、収まらない内容は警告される。
- 既存の写真管理、記事生成、PNG保存、クリップボードコピーを維持する。
- 自動テストを追加し、可能な範囲で実行する。

## 開発環境の制約

既存のAGENTS.mdを最優先で遵守。特に既存の `.venv` を作成・削除・再生成・変更しない。明示的な許可なく `uv sync` や `uv run` 等、既存 `.venv` に影響しうるコマンドを実行しない。検証が必要なら既存環境を変更しない方法を選び、必要に応じて別の仮想環境を使用する。不要な依存追加を避ける。
